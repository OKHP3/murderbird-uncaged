# Cranial lift-back proposal screen

This is a read-only comparison from the exact V6 native (`cb811241d241b0f18f529979b77635caecb83284b8b4df29c7564d4d2bf55eec`). At each of 41 fractions, the baseline uses cranial-cover local Z += 0.08 m × f. The single proposed path adds local Y += 0.05 m × `f*f*(3-2*f)`; +Y is rear. Both begin at the exact closed-state transform, and every other pivot stays fixed. These are prescribed native rigid states, not captured runtime poses.

The proposed path is **held, not recommended for implementation**. Across 6,435 possible mesh-pair identities in the head-region owner set with at least one cranial-cover mesh, it yields 0 new strict identities, 111 inherited (102 same-owner, 9 different-owner), and 2 resolved identities. Both resolved pairs are the left and right cere-root-transition intersections with crown lamina 0. The peak different-owner strict pair count is 7 for both paths. The rearward path moves the hood/crown conflicts later: the overlapping nasal hood remains strict through opening 0.775, compared with 0.50 in the vertical path; both hood fixings also return later, at 0.45 through 0.75/0.775. This trades away some mid-sweep cere-root conflicts but extends hood/crown interference. Closed-state interference is unchanged: the overlapping nasal hood strictly crosses crown lamina 0 and two crown-root pins at f=0.

The five known different-owner crown/hood/cere identities are recorded individually in `lift-back-screen.json`. Both cere-root pairs resolve on the proposed path; the nasal hood and its two fixings persist, with the later opening ranges above. Same-owner pairs remain a separate category and are not treated as intended or acceptable embedding.

The broader counts differ from earlier 39-pair screens because this screen compares every pair in the head-region ownership scope with at least one cranial-cover owner (78 cranial-cover meshes plus 44 meshes owned by head, upper-bill, jaw, or builder-optics), rather than a selected list of brows, mounts, temporal/crown parts, and fixings. Both use the same frozen `proper_crossing_receipt` strict kernel. BVH overlaps are candidates; strict receipts count noncoplanar edge-through-face crossings, so coplanar/tangent contacts and full containment are not established as clear or intersecting by absence of a strict receipt.

The path is only an access-motion proposal. Full containment, continuous swept-volume clearance, runtime behavior, and physical guidance are untested. A real support/guide mechanism would be required before implementing a prescribed rearward cover path. No native or runtime file was edited; no V8/V9 work was changed.
