# MB-P17 browser diagnostic procedure

**Candidate boundary:** current V37 exhibit only. This is a repeatable procedure for a later authorized visible check, not a report that these steps were executed. Use a desktop browser at a known viewport, a clean reload, and record exact URL, browser/version, viewport, timestamp, console/network errors, and whether the session used the built local app or a deployed URL. Do not substitute the retained CG assessment page for the interactive V37 exhibit.

## Desktop WebGL path

1. Open the V37 exhibit (`index.html` locally or its separately verified deployment URL). Record the served revision and whether the WebGL canvas initializes. Check the visible era label, loading/status text, and that the enclosure is visible around the bird.
2. Select Maker. Confirm the UI label and selected state; verify only the five levers and release-all control are offered, and Advanced-only reach/jump/thrust/claw controls are hidden. Move one lever and release it; use source-controlled behavior as a hypothesis, and record actual displayed motion separately.
3. Select Mechanic. Confirm era label, Engage/Stop/Wind controls, charge display, and absence of Advanced response controls. Engage, observe at least two complete route/cycle intervals if practical, stop, and wind. Record timing and any discrepancies; do not infer mechanical authenticity from labels.
4. Select Advanced. Confirm era label and Advanced controls. Test left, center, and right visitor positions with Reach; test early Retreat and retreat after visible commitment. Separately exercise Claw scrape, Power jump, Shield thrust, pause/resume, and reduced motion. Note actual visible outcome and state/status text for each.
5. Exercise camera by drag, scroll, pinch if touch hardware is available, arrow buttons, zoom buttons, keyboard arrows/plus/minus, and Home reset. Record which inputs worked and whether the model/enclosure remains in frame.
6. Select each part in the inspector, use Center selected part, and compare the visible highlighted/centered feature to the label. Do not score similarity from the copy alone.
7. Open inspection; wait for the settled transition before moving the separation slider. Separate, reassemble, and return. Record whether the scene reaches the assembled state and whether the enclosure and body remain readable. This is current-candidate observation, not successor acceptance.
8. Repeat era switching while paused and during a response/inspection transition. Check that pending transitions settle safely and labels/controls match the selected era.

## Forced illustrated fallback

1. Load the same path with `?view=illustrated` (remove any conflicting `view` parameter). Record that the fallback caption identifies a fixed view and the retry control is shown.
2. Switch Maker, Mechanic, Advanced; select part descriptions and toggle the illustrative assembly diagram. Check era-still changes, caption/alt text, and that diagram labeling continues to say illustrative/not 3D.
3. Try the camera controls only to document the fallback limitation; do not call a static image an orbitable view. Use Retry 3D and record whether it returns to WebGL or remains in fallback.
4. Separately force model/WebGL failure only in a disposable local diagnostic environment, if available. Record console/network failure and recovery. Never modify source or deployment just to induce failure.

## Identity and responsive observations

- Compare each era only to its scoped references: locked composite for full-bird identity; candidate 03 for prior common body direction; July selection for head identity; each era image for finish; First Choice clip only for surface continuity/screen presence, with frame timestamps recorded.
- Record identity observations as human reviewer notes with reference IDs and exact frames/views. Do not convert control functionality, source strings, a passing state test, or this script into artistic acceptance.
- Repeat at narrow mobile width in an actual browser/device separately. Record viewport, touch behavior, overflow, control visibility, load failures and performance. Emulation is not physical-device evidence.

## Result fields

For every step: `PASS`, `FAIL`, `NOT RUN`, or `UNKNOWN`; exact evidence/capture path; current candidate/revision; environment; issue/limitation; next check. Keep local source/test evidence separate from browser, mobile, human, deployment, and acceptance evidence.
