The managed worktree already contains a Blender-built full-body study and a Three.js scene; the current *presence* derivative is also under active local development. ## Authoring and browser boundary

Blender should own detailed editable plates, hidden interior parts, named rigid assemblies, hinge pivots and animation studies. Keep the `.blend` outside the public build. Export a deliberately optimized GLB with a stable named hierarchy for the app; keep the editable file as source, not as the website asset. Three.js already has the `GLTFLoader` add-on and `AnimationMixer`; the live implementation instead directly controls named group transforms for the bounded encounter/inspection behavior. The documentation confirms loader support and imported animation clips, not that any particular Blender rig or export will behave correctly—validate the actual files in this app. [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html), [AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html), [local package manifest](../package.json).

Unreal would change the deployment model. Epic documents Pixel Streaming as running the Unreal application on a desktop/cloud host and streaming audio/video to browsers over WebRTC; its stack includes web/signaling components and may need STUN/TURN for network traversal. This can provide higher server-rendered scene complexity, but it adds GPU hosting, networking, bandwidth, latency and operational work. It is not a static Vite/Three build and no hosting budget or stream service is authorized. Treat Unreal as a separately scoped migration only if measured browser limits block the exhibit—not as an asset-authoring requirement. [Epic Pixel Streaming](https://dev.epicgames.com/documentation/unreal-engine/pixel-streaming-in-unreal-engine), [architecture and networking overview](https://dev.epicgames.com/documentation/unreal-engine/overview-of-pixel-streaming-in-unreal-engine), [infrastructure components](https://dev.epicgames.com/documentation/unreal-engine/pixel-streaming-infrastructure).

## Original proposed no-upload experiment

Use only the already-present local study files and approved repository references. In the current Blender script, make one reviewable **contact-behavior** pass: inspect the bird at matched front and three-quarter views; key a grounded neutral stance, noticing, tucked rib shield, short shoulder/elbow shove, and recoil/recovery; preserve the constrained left shoulder and the compact opposing counterbalance. Do not add flight, flapping, human Mixamo motion, or guessed historical internals. Export a local GLB and load it through the existing Three.js path. Check joint clearance, visible part names, cage contact/reach, reversible inspection while paused, file size, draw calls and frame rate on the actual supported browser/fallback. Keep the source `.blend`, captures and measurements local; no source image/model leaves the machine. This tests whether authored segmentation and timing read clearly before surface-detail work. It does **not** establish physical force, balance, collision fidelity, owner approval or finished likeness. Do not spend credits, start trials, install plug-ins, download marketplace models, publish, or change runtime dependencies for this experiment.
